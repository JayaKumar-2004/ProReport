CHAPTER 1: INTRODUCTION

1.1 Introduction to Raksha-Suraksha

The rapid evolution of mobile technology has brought unprecedented convenience, but it has simultaneously introduced critical vulnerabilities regarding device theft, data breaches, and personal physical security. Traditional anti-theft applications heavily rely on active internet connections, rendering them completely ineffective the moment a device is taken offline by a malicious actor.

To bridge this critical security gap, the "Raksha-Suraksha Tactical Command System" was developed. Raksha-Suraksha is an enterprise-grade, bidirectional command-and-control (C2) platform engineered to secure remote physical mobile hardware. The system utilizes a hybrid architecture, combining the high-speed data synchronization of Firebase Realtime Database for active-internet scenarios with an encrypted Offline SMS Telemetry protocol for disconnected environments. This dual-layer approach allows authorized agents to monitor live GPS locations, trigger hardware alarms, access camera/microphone feeds, and wipe sensitive data seamlessly from a centralized web terminal.

1.2 Problem Definition

Currently available device tracking solutions inherently suffer from a "single point of failure" architecture: they require continuous Wi-Fi or Cellular Data connectivity to function. When a mobile device is compromised, the standard operating procedure for unauthorized users is to immediately disable internet access or remove the primary SIM card, permanently severing the connection to cloud-based tracking services.

Furthermore, existing solutions lack granular hardware control, preventing owners from actively securing their physical surroundings or gathering discrete multimedia evidence of the perpetrator. There is an urgent requirement for a resilient security ecosystem that can maintain command authority over a target device even in offline states, executing critical locking and tracking payloads without reliance on standard IP networks.

1.3 Objectives

The primary objective of this project is to architect and deploy a highly secure, multi-module web terminal capable of asynchronous communication with mobile companion nodes. The specific objectives include:

a) Real-Time Telemetry: To develop a Live Satellite Radar module that provides sub-10 second GPS coordinate updates, trail visualization, and geofencing alerts.

1.4 Scope

The scope of the Raksha-Suraksha project encompasses the full-stack development of a web-based command dashboard and its integration protocols for mobile environments. The system features modular architecture, specifically including Master Control, Live Radar Mapping, App Linking, and Message Control modules. The project focuses heavily on creating a responsive, high-performance UI/UX to ensure operational efficiency for the end-user across both desktop and mobile viewports, prioritizing security, low-latency command execution, and system reliability.

2.2 Existing System

Advanced users frequently employing security tools rely on dedicated software applications like "Find My Device." While these applications offer basic functionalities (ringing, wiping, locating), they heavily rely on active internet connections to function, which is their primary point of failure. They also fail to provide deep hardware overrides, such as secretly activating the microphone or taking photos without turning on the screen.

2.3 Proposed System

The proposed Raksha-Suraksha system replaces outdated, single-layer security concepts with a robust, hybrid-cloud architecture. By using asynchronous Firebase listeners and secure REST APIs, the web terminal can instantly push command states to the mobile node. If the internet connection drops, the proposed system automatically falls back to an encrypted SMS gateway. The companion mobile node continuously listens for these state changes via background "Ghost Services" and executes hardware overrides locally, creating a foolproof, closed-loop security environment.

Software Requirement: Backend: Python / Java (Android Native), Google Firebase (Realtime DB & Authentication). Frontend: HTML5, CSS3 (Glassmorphism UI), Vanilla JavaScript. Database: Firebase Realtime Database (Cloud), SQLite (Local Mobile Storage).

CHAPTER 3: SYSTEM ANALYSIS AND DESIGNING

3.1 System Requirement Specification

The System Requirement Specification (SRS) dictates both functional and non-functional requirements.

Functional Requirements: The system must allow users to log in securely, view live GPS coordinates on a map, trigger remote alarms, and generate encrypted SMS payloads to send to offline devices.

Non-Functional Requirements: The system requires a highly responsive User Interface (UI) that scales perfectly on mobile devices. It demands a command-execution latency of <50ms on active internet, 99.9% uptime SLA through Firebase, and 256-bit TLS encryption for all data traversing between the web terminal and the mobile device.

3.2 System Architecture

The Raksha-Suraksha architecture operates on a Three-Tier Client-Server model.

The Client Tier (Web Terminal): A responsive UI where the "Agent" inputs commands.

The Intermediary Tier (Firebase/SMS Gateway): Acts as the secure bridge. Commands are pushed as state changes to the Firebase tree or formatted into encrypted SMS strings.

The Hardware Tier (Mobile Node): The Android application running a continuous background "Ghost Service." It listens for changes in the Firebase tree or incoming SMS triggers, decodes the command, and interacts directly with the device's native APIs (Camera, GPS, AudioManager).

3.3 System Design Data Flow Diagram

In the Raksha-Suraksha Data Flow process:

Level 0: The User authenticates into the Web Terminal.

Level 1: The User inputs a command (e.g., "Trigger Alarm"). The Web Terminal processes this and updates the database node.

Level 2: The Firebase cloud triggers an onDataChange event on the target mobile device.

Level 3: The mobile device's background service intercepts the event, executes the hardware override (sounds the alarm at max volume), and writes a success confirmation back to the database, which immediately updates the User's Web Terminal.

CHAPTER 4: IMPLEMENTATION

4.1 Implementation Strategy

The implementation strategy followed an Agile development lifecycle, allowing for iterative testing of discrete modules. The strategy prioritized the "Core Engine" first—establishing the stable connection between the Web Frontend and Firebase. Once authentication and database reading/writing were verified, the physical Android implementations (Camera API, GPS Location Manager, SMS Broadcast Receiver) were developed and tied to the database listeners. Finally, the UI/UX was polished using modern CSS frameworks to provide an enterprise-grade aesthetic.

4.2 Methodology

The methodology relies heavily on an Event-Driven Architecture. Instead of the mobile device constantly draining the battery by "asking" the server if a command is ready, the system uses Firebase's WebSocket connections. The mobile device stays asleep until the server "pushes" a command event to it. For offline scenarios, the methodology uses a custom BroadcastReceiver in Android that intercepts incoming SMS messages, scans them for a specific cryptographic hash, and executes the hidden command without ever notifying the thief that a message was received.

4.3 Module Description

The Raksha-Suraksha platform is divided into several highly specialized tactical modules:

Master Control Module: The central hub where agents can trigger remote alarms, lock the device screen, or initiate factory data wipes.

Live Radar Map Module: Integrates mapping APIs to plot real-time GPS coordinates fetched from the mobile device, allowing agents to track movement trails and set geofence boundaries.

Tier-3 Evidence Vault: A secure interface that retrieves and displays intercepted media. If the mobile device captures a photo of the unauthorized user or records ambient audio, it uploads the files to Firebase Storage, which are then accessible via this vault.

Message Control Module: The SMS payload generator. It encrypts commands into text strings that can be manually sent from any standard phone to the target device when it loses internet access.

App Linking Module: The synchronization gateway that pairs the unique ID of the mobile application instance with the authenticated web dashboard user, ensuring commands are only routed to authorized hardware.

package com.rakshasuraksha.app.services;

import android.app.Service;
import android.content.Intent;
import android.os.IBinder;
import com.google.firebase.database.DatabaseReference;
import com.google.firebase.database.FirebaseDatabase;
import com.google.firebase.database.ValueEventListener;
import com.google.firebase.database.DataSnapshot;
import com.google.firebase.database.DatabaseError;

public class GhostService extends Service {
    private DatabaseReference commandRef;

    @Override
    public int onStartCommand(Intent intent, int flags, int startId) {
        commandRef = FirebaseDatabase.getInstance().getReference("CommandNode");
        listenForCommands();
        return START_STICKY;
    }

    private void listenForCommands() {
        commandRef.addValueEventListener(new ValueEventListener() {
            @Override
            public void onDataChange(DataSnapshot dataSnapshot) {
                String command = dataSnapshot.getValue(String.class);
                if (command != null) {
                    executePayload(command);
                }
            }

            @Override
            public void onCancelled(DatabaseError error) {
                // Failed to read value
            }
        });
    }

    @Override
    public IBinder onBind(Intent intent) {
        return null;
    }
}

// SmsCommandReceiver.java (Offline Telemetry)
package com.rakshasuraksha.app.receivers;

import android.content.BroadcastReceiver;
import android.content.Context;
import android.content.Intent;
import android.os.Bundle;
import android.telephony.SmsMessage;
import com.rakshasuraksha.app.utils.HardwareOverride;

public class SmsCommandReceiver extends BroadcastReceiver {
    private static final String SECURE_HASH = "RX-882";

    @Override
    public void onReceive(Context context, Intent intent) {
        Bundle bundle = intent.getExtras();
        if (bundle != null) {
            Object[] pdus = (Object[]) bundle.get("pdus");
            for (Object pdu : pdus) {
                SmsMessage smsMessage = SmsMessage.createFromPdu((byte[]) pdu);
                String messageBody = smsMessage.getMessageBody();
                
                if (messageBody.contains(SECURE_HASH)) {
                    parseAndExecute(context, messageBody);
                }
            }
        }
    }

    private void parseAndExecute(Context context, String payload) {
        if (payload.contains("ALARM_ON")) {
            HardwareOverride.triggerMaxVolumeAlarm(context);
        } else if (payload.contains("WIPE_DATA")) {
            HardwareOverride.initiateFactoryReset(context);
        }
    }
}

CHAPTER 6: SOFTWARE TESTING

There are many different testing levels which help to check behavior and performance for software testing. These testing levels are designed to recognize missing areas and reconciliation between the development lifecycle states.

6.1 Unit Testing

A unit testing is a smallest testable portion of system or application which can be compiled, located, and executed. This kind of testing helps to test each module separately. This kind of testing is performed by developers.

6.2 Integration Testing

Integration means combining. Different software modules are combined and tested as a group to make sure that the integrated system is ready for system testing. Integrating testing checks the data flow from one module to other modules.

6.3 System Testing

System testing is performed on a complete, integrated system. It allows checking system compliance as per the requirements. It involves load, performance, reliability and security testing.

6.4 Acceptance Testing

Acceptance testing is a test conducted to find if the requirements of a specification or contract are met. Acceptance testing is basically done by the user or customers.

6.5 Types of Testing: Black Box & White Box

Black Box Testing is defined as a testing technique in which functionality is tested without looking at the internal code structure. White-box testing is a method that tests internal structures or workings of an application.
